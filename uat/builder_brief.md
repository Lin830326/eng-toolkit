# Brief for scenario builders

Repo worktree: C:\Users\USER\Documents\GitHub\eng-toolkit\.claude\worktrees\feat-uat (branch feat/uat). Use `.venv\Scripts\python.exe` (never uv). Do NOT run git commands that write; leave files uncommitted. Read `uat/README.md` and `scripts/uat_run.py` first.

Goal: build realistic user-acceptance scenarios for the eng-toolkit MCP server (101 engineering tools, see `plugin/skills/eng-toolkit/SKILL.md` for the tool map and the domain skills under `plugin/skills/`). A simulated person will work with an AI assistant (Claude Haiku, with the plugin) and we will judge whether the person got a correct, useful answer or picture. We want to find where the toolkit and the skills fail a REAL user, so the scenarios must not be toy exercises:

* Use REAL artifacts and real-world parameters. Real files are on this machine: KiCad 10 demos and templates under `C:\Users\USER\AppData\Local\Programs\KiCad\10.0\share\kicad\demos` (pic_programmer, video, ecc83, microwave, stickhub, simulation/...) and `...\share\kicad\template` (Arduino_Uno, Arduino_Nano, BeagleBone-Black-Cape ...); real STEP models under `...\share\kicad\3dmodels\*.3dshapes` (Heatsink, Connector_*, Package_*, Inductor, Battery ...); `tests/pcb_fixtures`, `tests/cad_fixtures.py`. Programs: `C:\Users\USER\AppData\Local\Programs\KiCad\10.0\bin\kicad-cli.exe`, conda env eng-eda (ngspice, gmsh, ccx: see C:\Users\USER\.claude\projects\C--Users-USER-Documents-GitHub-eng-toolkit\memory\eng-toolkit-external-tools-installed.md), Yosys in `C:\Users\USER\tools\oss-cad-suite-root\oss-cad-suite`. For non-file domains use parts and numbers a working engineer would really have (a named motor/pump/steel section/bearing/fastener/thermistor with its datasheet values; a real gearbox shaft; a real cooling loop), not round textbook numbers.
* The task needs several steps or a judgement call (choose a model, fix a missing input, interpret a refusal, compare two options), and at least half of the scenarios end with a picture or file the person wants (chart, drawing, 3D view, gerbers ...).
* The person is imperfect: vague first message, missing or wrong units, sometimes Chinese (Traditional) or mixed language, asks for something slightly outside what the tools do, or gives a wrong assumption the assistant should catch. Put what they know but won't volunteer into `facts`.
* There must be an INDEPENDENT truth: a script `uat/truth/<id>.py` that prints JSON `{"answers": {...}, "how": "...", "tolerance": "..."}` computed WITHOUT eng-toolkit tools (kicad-cli, standalone ngspice / Yosys / CalculiX, scipy, numpy, a closed-form textbook formula, or a published number with its source). Run it and make sure it works. Where a hand calculation needs a modelling choice, state the choice and the tolerance. Where the right answer is "the tool can't do that, say so", the truth says that.
* Verify each scenario is solvable: confirm with a quick direct call of the tools (in-process: `from fastmcp import Client; from eng_toolkit.gateway.server import gateway; await c.call_tool(name, args, raise_on_error=False)`, set env ENG_TOOLKIT_WS to a folder under scratch_bench/) that the tools can produce the answer, and note in the scenario file a `"tool_check"` field with what you observed (numbers) and any rough edge you hit (that is already valuable: report it).
* Do NOT run `scripts/uat_run.py` for the whole set (the coordinator does); you may run it once on one scenario with `--out scratch_bench/uat_try --workers 1` to check the file works end to end.

Write per scenario: `uat/scenarios/<id>.json` (schema in uat/README.md, ids start with your prefix) and `uat/truth/<id>.py`. Files with real paths must use forward slashes. Final reply: for each scenario one line (id, what the person wants, what the truth is), plus any tool/skill rough edge or bug you found while verifying (with the exact input), and what you could not make realistic. Touch nothing outside `uat/` and `scratch_bench/`.
