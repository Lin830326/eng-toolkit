# The `spice` domain: circuit simulation with ngspice

Code: `eng_toolkit/domains/spice/` (`netlist.py` the allow-list parser, `engine.py` deck building and ngspice run, `tools.py` `spice_simulate` and `spice_check_netlist`, `measure.py` `spice_measure`, `engines.py` registers `EXTERNAL_TOOLS = (NGSPICE,)` from the shared catalog). Tests: `tests/test_spice_*.py` (see "Tests" for the counts), helper `tests/spice_fixtures.py`. The program is ngspice (BSD-3-Clause), found and started only through `eng_toolkit/external.py`; the toolkit never imports, links or ships it. Read `docs/external/design.md` first for what the layer does and does not do.

## Tools

| Tool | Starts ngspice | What it returns |
|---|---|---|
| `spice_simulate` | yes | `op`: one value per output. `dc`, `ac`, `tran`: `<output>.min`, `.max`, `.final` per output (ac: of the magnitude) as `values`, the whole table as artifact `result.csv`, per-output summary (where the min and max are) in `data.summary`. Also artifacts `netlist.cir` (the circuit exactly as sent), `deck.cir` (what ngspice ran), `ngspice.log` |
| `spice_check_netlist` | no | `values.elements` and `values.nodes`; `data`: elements by letter, nodes, models, subcircuits, `runnable`, `problems` (line, code, message), the limits and the allow-list; warnings for floating nodes and nodes without a DC path |
| `spice_measure` | no | one value derived from a table (`result.csv` or any CSV with a header): `steady_state`, `rise_time`, `fall_time`, `overshoot`, `settling_time`, `bandwidth_3db`, `bandpass_3db`, `value_at`; the formula and the intermediate numbers in `data` |

`spice_simulate` and `spice_check_netlist` require exactly one nonblank source, `netlist` or `netlist_file`. Giving both returns `input.invalid` naming both parameters before file access or simulation. Giving neither returns the existing `input.missing` error. `tests/test_spice_inputs.py` covers both tools directly and through the gateway client, including existing and missing file paths.

All parameters are strings with units (`"10 us"`, `"1 kHz"`, `"0.5 V"`), integers or booleans; output names are `v(node)` (a node of the top level) and `i(name)` (a top-level voltage source or inductor). Results follow the unified contract; every output has `review_status: unreviewed`. Error families added: `input.netlist_refused` (the allow-list), `input.netlist_invalid` (the netlist parses but cannot be simulated: no ground, missing model...), `measure.not_found` (the table does not contain what the measurement needs); the rest are the existing `input.*`, `units.*`, `engine.*`.

**Sign convention (ngspice, as in every SPICE).** The current of a voltage source is positive when it flows *into* its + terminal, so a source driving a load shows a negative current: 5 V across 2 kOhm gives `i(v1) = -2.5 mA`. The inductor current `i(l1)` is positive from its first node to its second. The convention is stated in `data.sign_convention` of every `spice_simulate` result.

**Analyses come from parameters, never from the netlist.** The netlist may not hold `.tran`, `.ac`, `.dc`, `.op`, `.print`, `.plot`, `.save`, `.meas`; a deck is built from validated numbers (`repr` of a float rounded to 12 significant digits).

## Security: the netlist is data

An ngspice netlist is a program. `.control ... shell ...` runs commands, `.include`/`.lib` read any file, `.osdi`/`.pre_osdi` and the XSPICE A devices (and the OSDI N devices) load compiled code, `.write` and `wrdata`-style commands write files, `source`/`set`/`echo`/`exec` are commands, `external` sources and `file=` read data from outside. The design is: **the caller's text is parsed, never forwarded.** What goes to ngspice is `deck.cir` = a fixed title + the accepted lines rewritten in a normal form + a control script this module writes from validated parameters + `.end`. What was checked is what runs, because the checked, rewritten text is what is emitted.

Steps in `netlist.parse` (all before anything is run; a refusal starts no program, which the hostile tests prove with a recording fake program):

1. **Intake.** Text must be valid UTF-8 (a file with other bytes is `input.invalid`, with the byte offset), 200 000 bytes at most (a 5 MB netlist is `input.too_large`), 5000 lines, no control character other than tab, LF, CR (NUL is named in the message).
2. **Lines.** Line 1 is the title and is **never forwarded** (the deck gets its own title). A title starting with `.` is refused (`.include x` as a title). Comment lines `*` and inline comments (`;`, `//`, `$` after a blank) are dropped, then `+` continuation lines are joined to the line above **before** any check, so `.con` + `trol` or `R1 a 0 1k` + `.control` is seen whole. Tabs become blanks, everything is lower-cased (SPICE is case-insensitive, and this makes `.CoNtRoL` and `\t.CONTROL` the same string), blanks around `=` are removed. A non-ASCII character in a circuit line is refused *before* lower-casing (U+212A KELVIN SIGN would otherwise lower-case to an ASCII `k`); non-ASCII is fine in the title and in comments because neither is forwarded.
3. **Classification of every logical line** by its first token, exact match: a directive must be one of `.model .param .subckt .ends .global .ic .nodeset .temp .options/.option .end`; an element must begin with one of `R C L V I D Q M J S W T K X E F G B`. Refused with a reason: every other directive (`.control .endc .include .inc .lib .osdi .pre_osdi .write .save .csparam .print .plot .meas .tran .ac .dc .op .noise .func .if .title .probe`, and anything else, abbreviated or not), the letters A (XSPICE code model), N (OSDI), O, P, U, Y, Z, and any line starting with another character. Text after `.end` is refused. A directive-like word (`.name`) *inside* a line is refused (hidden behind a continuation).
4. **Character set.** An accepted line may contain only `a-z 0-9 space _ . , + - * / ^ ( ) = < > ! & | { } ' [ ] : # @ ~ ?`. No backslash (so no Windows path), no `"`, backtick, `$`, `;`, `%`, nothing non-ASCII.
5. **Words.** `file`, `filename`, `external` (external sources), and the random functions `gauss agauss unif aunif rand rnd sdrnd trnoise trrandom` (a run must be repeatable) may not appear anywhere in an accepted line. An element may not be *named* like an ngspice command (`shell`, `system`, `source`, `exec`, `echo`, `set`, `unset`, `write`, `load`, `codemodel`, `osdi`, `edit`, `wrdata`, `wrs2p`, `hardcopy`, `spice`, or an abbreviation of three letters or more): these only run inside `.control`, which is refused, so this is defence in depth and removes a way to read an accepted netlist as a command.
6. **Per-directive grammar.** `.model name type [key=value ...]` with type one of `r c l sw csw d npn pnp njf pjf nmos pmos nmf pmf vdmos`; `.param name=value` (a number, `{expression}` or `'expression'`); `.ic`/`.nodeset` take `v(node)=number`; `.temp` numbers in -273.15..1000; `.options` an allow-list of keys with ranges (`reltol abstol vntol chgtol trtol gmin itl1 itl2 itl4 method maxord temp tnom pivtol pivrel scale defl defw defad defas rshunt cshunt gminsteps srcsteps`; no `post`, `list`, `node`, `savecurrents`...); `.subckt`/`.ends` with nesting at most 3.
7. **Numbers.** Every numeric literal with its SPICE suffix (`k meg m u n p f a t g mil`) must be zero or between 1e-30 and 1e30 in magnitude; otherwise `input.out_of_range` naming the line (a 1e308 resistor, `1e999`, a `1e-40` capacitor).
8. **Work caps.** At most 1000 elements *after* expanding subcircuit instances (computed by counting, never by expanding: ten levels of ten instances is 10^10 and is refused instantly; recursion is refused); at most 100 000 points for a DC sweep or a transient (the count is `(stop - start) / step + 1`, so a transient asking for 10^12 points is refused with the count and the limit); at most 500 points per decade and 50 000 points for an AC sweep; at most 16 outputs; the run is killed after 60 s, with a 2048 MB memory cap (Windows Job Object), 40 MB of files written and 1 MB printed, all by `eng_toolkit.external.run`.
9. **Refusal messages** name the line number and the directive, never echo more than 80 characters of the line (the directive is cut to 40), and are under 600 characters in total.

What the run itself adds:

* The command line is `ngspice_con -b -o <job>/ngspice.log <job>/deck.cir`, built from `Path` objects inside the job directory (the layer refuses any other `PathLike`). No data from a netlist is in the command line; the test records the argument list and compares it with this form.
* The child environment is the layer's scrubbed one: no API keys or `ENG_TOOLKIT_*`, `HOME`/`USERPROFILE`/`APPDATA` inside the job directory, so a `~/.spiceinit` of the user is not read; the working directory is the job directory, which holds no `.spiceinit`; the netlist file copy (`netlist_file`) is in `input/`, not in the working directory.
* The control script is fixed: `set wr_singlescale`, `set wr_vecnames`, `set numdgt=15`, the analysis command, `wrdata table.csv <outputs>`, `quit`. The output names were matched against `v(<node of the parsed circuit>)` and `i(<voltage source or inductor of the parsed circuit>)`.
* ngspice exits 0 when the circuit is wrong (an unknown vector, a missing model, a singular matrix with a result after gmin stepping). Success is therefore: the table exists, parses, has the expected shape, holds only finite numbers, and the log has no `Error` line, `Timestep too small` or `simulation interrupted`; otherwise `engine.failure` with ngspice's own words (cut to 240 characters, the job directory replaced by `<job>`). `Warning:` lines (at most 5, de-duplicated) are passed on as warnings. No `inf`/`nan` ever reaches a result (a table value that is `nan` or `inf` is an `engine.failure`; the tests call through `fastmcp.Client` and check the payload with `allow_nan=False`).
* Files go through `JobHandle.input_file` (`netlist_file`, `csv_file`): opened once, checked on the open file, the tool reads a copy; `ENG_TOOLKIT_READ_DIRS` applies.

### What this does not defend (honest list)

* **It is not a sandbox.** ngspice runs with the server user's rights. The allow-list is the barrier: a line that is accepted is not expected to reach any file, command or code loader, but the argument is "the grammar I accept contains no such construct", not "ngspice cannot do it". I did not read ngspice's source; the claim rests on the documented syntax and on the tests.
* **Expressions are evaluated by ngspice.** `.param`, `{...}`, `'...'`, B sources and E/G `value=` expressions go to ngspice's expression parser. Known functions are mathematical; I know of none that touches a file, but I did not audit the full function list of version 41, and I only refuse the random ones I know of. An expression can still produce `inf`/`nan` or a huge value at run time (caught on the way out), or be slow (caught by the time limit).
* **Memory-safety bugs in ngspice's parsers** (a crafted accepted line crashing or corrupting the process) are not prevented; the layer's time, memory and output limits and the separate process are the only containment. Keep ngspice updated.
* **ngspice's own start-up files.** ngspice reads `spinit` from its installation (`<install>/share/ngspice/scripts/spinit`, which in the conda build loads its code models) and `.spiceinit` from the home directory and the working directory. The home is redirected into the job directory and the working directory is a fresh job directory; the install's own `spinit` is trusted as part of the installation.
* **`.model` parameters** are accepted for any name (`key=number-or-expression`); `level=` picks among models compiled into ngspice. An `.osdi` model cannot be loaded (no `.osdi`, no `osdi` command), so a level that needs a loaded OSDI binary just fails.
* **A subcircuit can hide a lot of work** inside the 1000-element cap (devices with expensive models); the time limit is the bound.
* Windows is the only platform run. The Linux and macOS code paths of the layer are as unverified as the layer says.

## Numbers: exact, or dependent on the integrator

* **Exact up to rounding (about 1e-12 relative):** operating points of linear circuits; AC points of linear circuits (ngspice solves one complex linear system per frequency). The AC tests use a single frequency (`sweep="lin"`, `points=1`, `start == stop`) so that no grid or interpolation is involved: RC corner gain 1/sqrt(2) and phase -45 degrees agree to 3e-13 relative; the series RLC capacitor voltage at f0 equals Q to 3e-13.
* **Depends on the solver tolerances:** operating points with nonlinear devices (the diode: gmin 1e-12 S across the junction and ngspice's value of kT/q, the sixth digit of which differs from CODATA 2018, give a difference to the hand-solved Shockley equation of 3.1e-6 V; the test allows 5e-5 V).
* **Depends on ngspice's integration error and on the output spacing:** transient results. With `reltol=1e-3` (default) and the largest internal step limited to the output step (10 us for tau = 1 ms), the RC step response differed from `1 - e^(-t/tau)` by -1.2e-6 V at t = tau and +6.7e-7 V at 3 tau; the tests allow 1e-5 V. A larger step or a stiffer circuit gives larger errors; there is no error estimate in the result. The step function in the tests is a `PULSE` with a 1 ns edge, which shifts the curve by 0.5 ns (5e-7 tau); with `use_initial_conditions` the first stored row is the first accepted time point after 0, not t = 0 itself.
* **Depends on sampling:** every number in `spice_measure` (see below), and the `min`/`max` of a swept output (the maximum of a resonance peak is the maximum over the grid: the series RLC test with 400 points per decade finds 3.20215 against the closed-form peak 3.20256, 1.3e-4 low, at 4918 Hz against 4905.5 Hz).
* **Transient rows are ngspice's own time points**, not a uniform grid; the output step bounds the largest interval. Interpolate (the `value_at` measurement does) rather than index.
* AC columns: `re`, `im`, `mag`, `db` (20 log10 mag, floored at -400 dB so that a zero never gives -inf), `phase_deg` (wrapped to (-180, 180], not unwrapped).

### `spice_measure` formulas

`y` is the chosen column, `x` the first column, crossings by linear interpolation. `steady_state`: time-weighted (trapezoid) mean of `y` over the last `final_fraction` (default 0.1) of the x span. `D = y_final - y[0]` with `y_final` the steady state. `rise_time`: `t90 - t10`, the first times `y` reaches `y[0] + 0.1 D` and `y[0] + 0.9 D` (rising step only); `fall_time` the same for a falling step. `overshoot`: `100 (max y - y_final) / D` (`100 (y_final - min y) / |D|` for a fall), never negative. `settling_time`: the time (from the first sample) of the last entry into `y_final +- tolerance |D|` (default 2 %); an error if the last sample is outside. `bandwidth_3db`: the first frequency at which the gain is 10 log10(2) = 3.0103 dB below the gain of the *first* sample, linear in dB against log10(f) (so it is for a low-pass response; on a band-pass table it gives `measure.not_found` that points to `bandpass_3db`). `bandpass_3db`: the maximum-gain sample is the peak, and each corner is the crossing of peak - 3.0103 dB on its own side of the peak (linear in dB against log10(f)); the value is the bandwidth `f_upper - f_lower`, and `lower_corner_3db`, `upper_corner_3db`, `peak_frequency`, `peak_gain_db` and `center_frequency_geometric` are values too; a corner that the sweep does not reach is `measure.not_found` naming the other corner (checked on a second-order band-pass, f0 = 1 kHz, Q = 2: 780.78 Hz and 1280.78 Hz, bandwidth f0/Q). Units follow the column: `v(...)` volt, `i(...)` ampere, `.db` decibel, `.phase_deg` degree; on an ac table a bare `v(out)` is `v(out).mag` for every measurement. `value_at`: linear interpolation. The baseline `y[0]` is the first sample, which with `use_initial_conditions` is slightly after t = 0; a result is flagged when the last sample is more than 0.1 % of the step away from the steady-state mean ("still moving": a 5 tau record of an RC step otherwise reports a spurious 0.2 % overshoot). Measured against closed forms: RC rise time tau ln 9, 2 % settling tau ln 50, second-order overshoot exp(-pi zeta / sqrt(1 - zeta^2)), RC -3 dB frequency 1/(2 pi RC) (20 points per decade: 1.8e-4 relative low; 50 points per decade: well under the 5e-4 the test allows).

## Decisions and alternatives

* **Allow-list over deny-list.** A deny-list of dangerous directives is a list of what one remembered; ngspice has dozens of commands and abbreviations. The allow-list is a short grammar that I can state completely. Cost: legitimate netlists using `.include` of a model library, `.lib`, `.func`, `.if`, `.meas`, `.tran` lines, `.step`, `.noise`, `.tf`, `.pz`, `.sens`, A or N devices, temperature sweeps, Monte Carlo, behavioural `table`/`pwl file` sources or `.print` cards are refused. Models therefore have to be pasted in as `.model`/`.subckt` text (up to 200 KB).
* **Rewrite instead of validate-and-pass-through.** Passing the original text after checking it would let the checker and ngspice disagree about line boundaries, case, continuation, comments. Emitting the normal form removes the disagreement by construction.
* **A control script instead of dot-cards and `.print`.** `wrdata` with `set wr_singlescale` gives one table with full precision (`numdgt=15`) that is read by position; no scraping of printed text.
* **Three tools.** Simulation, a static check that needs no program (an LLM can iterate on a netlist without ngspice installed), and measurements on the table (kept out of ngspice's `.meas` so that no ngspice syntax from the caller is involved and the formulas are stated).
* **Outputs are limited to `v(node)` and `i(source)` of the top level.** `i(R1)` needs `savecurrents` (not allowed); subcircuit-internal nodes would need `x1.n` names; behavioural vectors (`@r1[i]`) are not accepted. A refused output is a clean `input.invalid` that lists the nodes that exist.
* **`.ic` with `use_initial_conditions`:** `.ic` is accepted; whether it is honoured follows ngspice (`uic`).

## Not done, not verified

* Not run on Linux or macOS. Only ngspice 41 (conda build, Windows) was used; other versions may print differently (the fatal-line patterns are `Error`, `Timestep too small`, `simulation interrupted`; these were seen or documented, not enumerated).
* Not covered: `.noise`, `.tf`, `.pz`, `.sens`, `.disto`, parameter sweeps (`.step`), temperature sweeps, Monte Carlo, S-parameters, multiple analyses in one call, a nonuniform `.tran` time step, `.lib` model files. No convergence aids beyond what ngspice does itself (the log's warnings about gmin stepping are passed on).
* A circuit that ngspice solves with a warning (singular matrix then gmin stepping) returns numbers and the warning; the numbers may be meaningless. The static check warns about nodes without a DC path before that happens.
* The floating-node check is per top-level node and treats every subcircuit instance as conducting; subcircuit bodies get no floating check. A MOSFET gate has no DC path; a node reached only by gates is reported.
* The 1000-element, 200 KB, 100 000-point, 60 s limits are my choices, not measured limits of ngspice. Memory use of a 100 000-point, 16-output run was not measured.
* The expression evaluator is not audited (see above). A real `claude -p --mcp-config` call with a small model was not made in this slice.
* `spice_measure` reads any CSV with a header; it does not check that the first column is a sensible x axis beyond "strictly increasing", and for a CSV that did not come from `spice_simulate` the unit of the result is guessed from the column name (`v(`: volt, `i(`: ampere, otherwise dimensionless).

## Gaps found in the shared layer (for the lead; nothing was edited there)

* `JobHandle` has no public accessor for the job directory; the tool takes `Path(handle.write_text(...).path).parent`.
* `external.run(check=True)` cannot be used for ngspice because the exit code is 0 for most failures; the domain reads the log itself (`-o`). The layer's `Record.stdout_tail` is only 3000 characters, too short to find an error; with `-o` the log is a file in the job directory.
* `external.clean_text` takes the paths to hide as pairs and `_hidden_paths` is private; the domain builds the pair for the job directory itself.
* The layer snapshots the whole job directory every 50 ms while the program runs (including `input/`); for a job with a large `result.csv` this is cheap, but it would not be for thousands of files.
