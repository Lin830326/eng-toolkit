# The `pcb` domain: KiCad boards and schematics

Code: `eng_toolkit/domains/pcb/` (`sexp.py` the S-expression reader, `boardread.py` the board reader, `schread.py` the schematic check, `program.py` staging and starting `kicad-cli`, `compute.py` the four computations, `tools.py` the server). Tests: `tests/test_pcb_*.py` (112 test cases: 19 reader, 12 board facts, 44 hostile inputs, 8 command lines and project-file filtering, 6 domain/registry, 23 against the real `kicad-cli`) and the fixtures in `tests/pcb_fixtures/` (`README.md` there says how each was made and what the hand-derived numbers are).

## The four tools

| Tool | Needs KiCad | Primary value | Other values | `data` |
|---|---|---|---|---|
| `pcb_info(board_path, max_listed=200, check_with_kicad=false)` | no (only for the cross-check) | `track_length_total` (mm) | `track_count`, `via_count`, `footprint_count`, `net_count`, `copper_layers`, `zone_count`, `board_width`/`board_height` (mm, only when Edge.Cuts has shapes) | format version, layers, outline extents, nets (pads/tracks/vias/length), footprints (reference, value, x/y, angle, side, pads), pads, tracks by layer and width, vias, zones, `parse_issues`, `ignored_elements`, optional `kicad_crosscheck` |
| `pcb_drc(board_path, use_project_files=true, min_clearance="", min_track_width="", refill_zones=false, max_violations=100)` | yes | `error_count` | `warning_count`, `unconnected_count`, `violation_count` | violations by type/severity and listed with items and positions, `unconnected`, `rule_set`, KiCad version, artifact `drc_report.json` (the raw report) |
| `pcb_erc(schematic_path, use_project_files=true, max_violations=100)` | yes | `error_count` | `warning_count`, `violation_count` | same shape, `position_calibration`, artifact `erc_report.json` |
| `pcb_export(board_path, export, layers="")` | yes | `file_count` | | `files` (name, bytes, sha256, format) for gerbers (+ `gerbers.zip`), drill (Excellon, mm), pos (CSV, mm), pdf, svg; every file is an artifact |

Counts are `dimensionless`, lengths `millimeter`. Every result carries `review_status: "unreviewed"`. No tool calls a language model, and nothing in a file is executed.

## What is exact, what depends on KiCad

**Exact (our arithmetic on the numbers in the file).** Everything `pcb_info` returns except the extents of a board whose Edge.Cuts shapes overlap: counts, segment lengths (hypot), arc lengths (radius times sweep from the three points), polygon areas (shoelace), positions, drills. Checked by hand in `tests/test_pcb_info.py`: the clean board has 3 tracks, 25 mm in total (10 + 10 on F.Cu, 5 on B.Cu), 1 via, 2 footprints, 4 pads, a 20 x 20 outline; the hand-written board gives an outline of 51 x 20 mm (a semicircle, a rotated footprint's circle), a 90-degree arc of radius 10 is 15.70796 mm, a 3-4-5 segment 5 mm, a zone 10 x 5 is 50 mm2. Where KiCad also gives a number (`pcb export stats` for board size, pad kinds, via kinds and minimum track width; `pcb export pos` for footprint positions) the two agree on the clean and clearance boards (`check_with_kicad`).

**Depends on KiCad's version and its rule defaults.** Every number of `pcb_drc` and `pcb_erc`, because the checks are KiCad's:

* With no project rules KiCad 10.0.6's built-in defaults apply. That was seen to mean a 0.2 mm minimum clearance and a 0.2 mm minimum track width, and a list of checks that are off (`data.rule_set.checks_disabled`: missing courtyard, track not centred on via, footprint filters, ...). Another version may differ; the result says `no project rules: KiCad <version> built-in defaults`.
* The descriptions of violations are in English because the tool writes `kicad_common.json` with `"language": "English"` into the job's own settings directory (without it the text follows the system language: the first runs came back in Traditional Chinese). The numbers behind them (`required_mm`, `actual_mm`, parsed from "clearance 0.2000 mm; actual 0.1000 mm") exist only when that English wording is matched; the `type` and `severity` fields never depend on text and are what the counts use.
* A violation has **no marker position of its own** in the JSON report. `x_mm`/`y_mm` are the positions KiCad gives for each item involved: a track's start, a pad's centre, a via's centre. For the clearance board (tracks N3 (5,5)-(15,5) and N4 (10,5.3)-(10,9), both 0.2 wide, gap 0.1 mm) the two items are at (5,5) and (10,5.3); the point where the copper is closest, (10,5.15), is not reported.
* Warnings such as `track_dangling` (a track end touching nothing) and `via_dangling` (a via with copper on one layer only) are part of the default rule set and appear on boards that are otherwise fine; the fixtures were built so that the clean board has none.
* **ERC coordinates.** `kicad-cli sch erc` 10.0.6 prints the position of every item 100 times smaller than the file's millimetres although the report says `"coordinate_units": "mm"` (a symbol at x = 100.33 mm is printed 1.0033). The tool does not assume this: it matches the `Symbol <ref> [...]` items of the report with the symbols of the file and applies the factor only if every match agrees (1, 10, 100, 1000 or 0.1, 0.01), and says what it did in `data.position_calibration`; otherwise the numbers are as KiCad printed them and the note says they are unverified. The positions of a DRC report were checked against the board file and are in millimetres.
* A board with no `Edge.Cuts` outline always gets one `invalid_outline` error; the tool adds a warning saying that this says nothing about the rest of the board.
* KiCad 10.0.6 loads a file with a `version` number from the future without complaint, and refuses a board with one copper layer (`1 is not a valid layer count`, exit code 3), which becomes `engine.failure` with its own message.

**Board extents differ from KiCad's in one case.** `outline.extents_mm` is the bounding box of the centre lines of every shape on Edge.Cuts (footprint shapes included, turned by the footprint's angle). KiCad's `pcb export stats` width is the width of the board *area*: a circle on Edge.Cuts that crosses the board edge is a cut-out there, and an arc is approximated by line segments (an error of up to 0.0025 mm was seen: 49.9975 against 50). The comparison therefore allows 0.005 mm and still reports the hand-written board `features.kicad_pcb` (a mounting-hole circle crossing the left edge) as a disagreement on `board_width_mm`: 51 against 49.9975. The gerber job file of KiCad adds half the line width on each side (20.1 for the 20 mm outline); this tool does not.

## The board reader (`sexp.py`, `boardread.py`)

* Iterative with its own stack, so a million `(` cannot exhaust Python's stack, and depth-limited besides: more than **64** levels is `input.invalid` (reason `depth`). A real board nests about 8 levels.
* Streaming: the root's children are handled one at a time and not kept; memory is the size of the largest footprint or zone, not of the file.
* Limits, all refused with a stable error: file over **50 MB** (`input.too_large`, checked on the open file by `JobHandle.input_file` before it is read); over **15 million tokens** or **1 million elements** (`input.too_large`); one string over **16 million characters** (`input.too_large`; text kept in a result is cut to 200 characters and control characters replaced); NUL byte, bytes that are not UTF-8, a PNG, text that does not start with `(`, unbalanced parentheses, unterminated strings, text after the root list (`input.invalid`, with line and column); a first list that is not `kicad_pcb` (`input.invalid`, with a pointer to `pcb_erc` for a schematic). Speed: about 7 MB/s (a 17.7 MB board of 130,000 segments took 2.4 s; the test reads 100,000 segments).
* **Numbers.** A number is a decimal token (`nan`, `inf`, `0x10` are not numbers: that element is skipped and listed in `parse_issues`). A number beyond **+-10,000 mm** (10 m; KiCad itself cannot place anything beyond +-2147 mm), or infinite (`1e999`), makes the whole file `input.out_of_range`: it is refused, never clamped, and no `inf` or `NaN` can reach a result (a final check also raises `engine.failure` if one ever did). The same limit applies to a schematic's coordinates, before KiCad starts.
* A damaged element (a word where a coordinate belongs, a missing width, a net id that is not declared) is skipped and listed (`parse_issues.count` is exact, the list holds the first 50), the rest of the board is still read.
* Formats: KiCad 5/6/7 syntax (`module`, nets by number, `fp_text`) and 8 to 10 (nets by name, `property`). `tests/test_pcb_info.py` reads the same board in the version-7 and the version-10 syntax and gets identical results.
* Not read: text, dimensions, images, groups, silkscreen graphics, zone fills (only whether a fill exists), pad shapes and sizes, stack-up, design rules in the board header, 3D model references. Elements the reader does not know are counted by name in `ignored_elements`.
* Footprint position is `(at x y angle)` as written: millimetres, y pointing **down**, angle positive counter-clockwise on the screen (the rotation of a footprint's own Edge.Cuts shapes uses KiCad's formula `x' = x cos + y sin, y' = -x sin + y cos`). `pcb export pos` writes y pointing up; the cross-check negates it.
* For an oval pad drill `(drill oval 0.8 1.6)` the first size (0.8) is listed.

## Starting kicad-cli: what it is given and what it may still read

The command line is built in `compute.py` from fixed words, files in the job's `work/` directory and **layer names read from the board's own layer table** (and also required to match `[A-Za-z0-9][A-Za-z0-9_.]*`, so `--output=x`, `F.Cu;calc`, a newline or `../x` fail even if a hostile board declares such a layer). `tests/test_pcb_command_line.py` records the argument list of every tool with a hostile file name and asserts that each argument is a fixed word, a layer list or a path inside `work/`, that the caller's own path never appears, and that none of `--define-var`, `-D`, `--drawing-sheet`, `--theme`, `--save-board`, `--variant`, `--schematic-parity`, `--exit-code-violations`, `--board-plot-params` is ever used. No caller string other than a number we format ourselves (`0.3` in `(min 0.3mm)`) reaches the program.

The board is copied by `JobHandle.input_file` (opened once, size and `ENG_TOOLKIT_READ_DIRS` checked on the open file) and again, under the fixed name `board.kicad_pcb`, into `<job>/work/`. The layer (`eng_toolkit/external.py`) gives the program a scrubbed environment, a 180 s limit (set by the domain; the layer default is 60), 4096 MB, 50 MB of written files, no stdin, and points `APPDATA`, `HOME` and the temp directories into `work/`.

What `kicad-cli` can therefore still read: the job directory (the board, the files we wrote there), KiCad's own installation directory (its stock libraries, templates and schema files), the operating system's fonts, and anything else the server's user can read; **it is not a sandbox**, and the layer says so. What it cannot see: the user's KiCad settings (`kicad_common.json` and the library tables sit in `APPDATA`, which is redirected, so **footprint and symbol library tables are empty**), the user's plugins and scripts, the user's environment variables (`KICAD10_*`, tokens). Consequences:

* **Footprint libraries.** A board holds its own copy of every footprint, so DRC works; the check that compares it with its library cannot, and reports `lib_footprint_issues` warnings when a footprint names a library. Likewise `lib_symbol_issues` in ERC (the symbol copy embedded in the schematic is used). Both are warned about in the result.
  These are not the design's findings, so `data.violations.library_warnings` (count and `by_type`) separates them (types `lib_footprint_issues`, `lib_footprint_mismatch`, `footprint_link_issues`, `lib_symbol_issues`, `lib_symbol_mismatch`), `data.violations.design_warnings` is the number of other warnings, every row has `group` `design` or `library`, the listing puts library rows after the real ones, and `values.library_warning_count` is added. `error_count`, `warning_count` and `violation_count` stay KiCad's own totals (library warnings included).
* **kicad-cli stops listing a kind of violation at a fixed number.** With KiCad 10 a board with 600 clearance violations reports exactly 499 at every threshold, and `track_width`, `track_dangling` and similar stop at 199 (the report has no flag for it; `--all-track-errors` only adds per-track errors, it does not lift the limit). A DRC count equal to 499 or 199 is therefore flagged: `data.violations.by_type[].at_kicad_limit`, the list `data.violations.at_kicad_limit` and a warning say the true count is at least that. ERC counts are not flagged (the ERC limits are not known).
* **3D models, drawing sheets, fonts of the user.** None of the exports offered (gerbers, drill, pos, pdf, svg) loads a 3D model, and no `--drawing-sheet` is passed, so a path inside the file to a model or a `.kicad_wks` file is not followed. No 3D, STEP, VRML or render export is offered.
* **Plugins and scripts.** None is enabled and none can be named by the caller (`--python-bom` and similar are not offered). A `.kicad_dru` rule is a rule, not a program.
* **Hierarchical schematics.** Only the one `.kicad_sch` is given to KiCad; sheets in other files are not copied and are not checked (a warning counts them). ERC of a whole hierarchy is not done.

### Project files next to the board (`use_project_files`, default true)

* `<name>.kicad_pro` is **not copied**. It is read as JSON (5 MB cap, `NaN` refused) and a new `board.kicad_pro` is written holding only: the numbers of `board.design_settings.rules` that are on an allow-list and within 0 to 1000, the severities of `rule_severities` (`error`, `warning`, `ignore`; keys `[a-z0-9_]{1,60}`), `drc_exclusions` (strings without control characters), the net classes (name and nine numbers) and `netclass_patterns`. For a schematic: `erc.rule_severities`, `erc.pin_map` (12 x 12 of 0, 1, 2) and `erc_exclusions`. Everything else (paths, `pcbnew.page_layout_descr_file`, library lists, text variables, appearance) is dropped; `data.rule_set.project_file.left_out` names the top-level keys that were. The test puts a path to `C:/Windows/win.ini`, a text variable and a library path in the project and checks none of them is in the file KiCad receives.
* `<name>.kicad_dru` (custom rules) is copied if it is at most 256 KB, UTF-8, and holds only `(version ...)` and `(rule ...)` lists at the top level (balanced, depth-limited) and `#` comment lines; anything else (an `(import ...)`, stray text) and the file is **not used**, with a warning. Rules are KiCad's rule language (conditions are expressions), not a program; as far as its documentation goes they cannot open files or start programs (not audited by us).
* Never copied: `fp-lib-table`, `sym-lib-table`, `.kicad_prl`, `.kicad_wks`, 3D models, anything else in the folder. Only the two names derived from the board's own name are looked at, through the same checked-copy path, so `ENG_TOOLKIT_READ_DIRS` and the size cap apply and provenance records them.
* `min_clearance` and `min_track_width` (lengths with units, 0 to 100 mm) become two rules we write at the end of the rules file (`toolkit_min_clearance`, `toolkit_min_track_width`) so they take priority over the project's. Hand check: the clean board's three tracks are 0.25 wide; `min_track_width="0.3 mm"` gives exactly 3 `track_width` violations and `"0.25 mm"` gives 0; on the clearance board a gap of 0.1 mm violates 0.15 and not 0.05.
* Exclusions saved in a project are carried over as strings (KiCad decides what they match; this was not tested with a real exclusion); `refill_zones=false` uses the fills stored in the file, which may be stale (a warning when the board has zones).

## Exports

`gerbers` plots the chosen layers (default: every copper, mask, silk, paste and Edge.Cuts layer the board has) and writes KiCad's job file; `gerbers.zip` holds those files with fixed timestamps (the Gerber files themselves carry the creation time, so two runs differ in hash). `drill` is Excellon in mm with absolute origin (y pointing up). `pos` is CSV in mm, both sides, y pointing up. `pdf` and `svg` are one page with the chosen layers on top of each other (`--mode-single`; for one layer per file call it once per layer), the svg cropped to the board area. A `.kicad_prl` KiCad writes beside the copy and its settings directory are not returned. File hashes are those of the layer's record and of the artifacts, and the tests recompute them.

## What was not done

* No board editing, no autorouting, no 3D (STEP, VRML, render), no BOM or netlist (those need the schematic and its libraries), no schematic parity check, no gerber/drill analysis, no zone refill of the board as a result (`--refill-zones` fills for the check and does not save).
* Hierarchical schematics (see above). Symbol and footprint libraries (see above).
* The reader is not a complete KiCad parser: copper-area, board-area-with-cut-outs and silkscreen questions are KiCad's.
* Verified on **one** KiCad (10.0.6) on Windows 11. Other versions (9.x, 11) may name violation types, print descriptions or lay out the JSON differently; the ERC coordinate scale may be fixed in a later version (the calibration is built to notice). The Linux and macOS paths of the layer were not run.
* Time and memory limits are the layer's (180 s, 4096 MB); a real DRC of a large board may need more, and the limit then shows as `engine.timeout`. A board near the 50 MB cap was not run through KiCad; 100,000 segments were run through our reader only.
* The ERC fixtures use a symbol from a library that is not visible, so both ERC results carry two `lib_symbol_issues` warnings by design.

## Notes for the shared layer's owner

* `JobHandle` has no public job directory; `program.job_dir()` reads `handle._job.dir`. A public property would remove that.
* `tests/test_external_registry.py` rejects any import line in `eng_toolkit/` containing the word `kicad` unless it also contains `external_catalog`; the module that starts the program is therefore called `program.py`.
* `external.run` creates a `KiCad/` folder (KiCad's "documents" directory) in the working directory besides the redirected settings; harmless, but it is in the job's file list.
* `external.version()` starts the program once per call (about 0.3 s); the domain caches it per program path for the life of the server.
